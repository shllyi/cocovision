COCOVISION SYSTEM ARCHITECTURE
==============================

1. SYSTEM OVERVIEW
------------------

CocoVision is a coconut-assistance platform composed of:

1. Frontend client
   - Expo and React Native application
   - TypeScript
   - Expo Router navigation
   - Supports Android, iOS, and web
   - Provides authentication, coconut image classification, acoustic analysis,
     community posts, market-price information, waste-product discovery,
     notifications, news, analytics, and AI chat

2. Backend API
   - Python FastAPI application
   - Asynchronous REST API
   - MongoDB database accessed through Motor
   - Machine-learning inference services
   - Authentication and user-management services
   - Cloudinary image storage
   - Google Gemini AI integration
   - News and market-data integrations

3. Machine-learning subsystem
   - YOLO object-detection model for coconut detection and counting
   - TensorFlow/Keras classifiers for coconut maturity classification
   - Acoustic analysis model for coconut evaluation
   - Separate training and dataset-preparation scripts

4. External services
   - MongoDB
   - Cloudinary
   - Firebase Authentication
   - Google Gemini
   - External news and market-data APIs
   - ngrok tunnel for development access
   - Expo/EAS for application execution and builds

5. BACKEND ARCHITECTURE
-----------------------

5.1 Backend bootstrap

The backend entry point is backend/main.py.

Responsibilities:

1. Creates the FastAPI application.
2. Enables logging.
3. Configures CORS.
4. Registers all API routers.
5. Configures Cloudinary.
6. Provides the root health endpoint.
7. Provides direct post retrieval.

Application title:

   Cocotry Backend

Health endpoint:

   GET /

Response:

   {"message": "Cocotry API is running"}

5.2 Backend configuration

Configuration is defined in backend/config.py.

Expected environment variables:

- MongoDB connection URL
- Database name
- Cloudinary cloud name
- Cloudinary API key
- Cloudinary API secret
- Gemini API key
- News API key

Actual secret values in backend/.env are intentionally not included in this
architecture document.

The backend also contains a Firebase service-account file. Its contents
must remain private and should not be committed to source control.

- malakanin

- Bounding box

Maturity interpretation:

- malauhog: Buko juice stage

8. DATA FLOW EXAMPLES
---------------------

8.1 User login

1. User enters email and password.
2. Frontend sends POST /auth/login.
3. FastAPI validates the request using the auth schema.
4. Auth service looks up the user in MongoDB.
5. Backend returns authentication/user information.
6. Frontend stores relevant session information using SecureStore.
7. Frontend redirects the user to the profile or main application area.

8.2 Coconut image classification

1. User selects or captures an image.
2. Frontend sends multipart image data to /classify/image.
3. FastAPI receives the UploadFile.
4. Classifier reads the image with Pillow.
5. YOLO detects coconut objects.
6. Each detected object is cropped.
7. The crop is normalized and resized.
8. The four-class model removes random/non-coconut detections.
9. Two maturity models classify the remaining coconut.
10. Backend returns count, detections, bounding boxes, labels,
    confidence values, descriptions, and image dimensions.
11. Frontend renders the result.
12. User may save the result through /user/save-scan.

8.3 Acoustic analysis

1. User records or selects audio.
2. Frontend uploads audio to /acoustic/audio.
3. Backend converts or decodes the audio if necessary.
4. Acoustic features are extracted.
5. The acoustic model produces a prediction.
6. Backend returns the acoustic result.
7. Frontend displays the analysis.

8.4 Community post creation

1. User enters post text and optionally selects images.
2. Frontend sends multipart data to /posts/create.
3. Backend validates the post request.
4. Images are uploaded to Cloudinary.
5. Cloudinary URLs are attached to the post.
6. Post metadata is saved to MongoDB.
7. Notifications may be generated for relevant users.
8. The new post is returned to the frontend.

8.5 AI chatbot interaction

1. User types a question.
2. FloatingChatbot sends POST /ai/chat.
3. Backend prepares the prompt.
4. Google Gemini processes the request.
5. Backend returns the generated answer.
6. The chatbot displays the answer.

8.6 Price prediction

1. User opens the price or prediction screen.
2. Frontend requests current prices, histories, or insights.
3. Backend loads stored or synchronized market data.
4. Market-analysis service processes the data.
5. Forecasting logic produces future estimates.
6. Backend returns chart-ready data and explanations.
7. Frontend renders price charts and insights.

12. ARCHITECTURAL STYLE
-----------------------

The system follows a modular monolithic architecture.

It is not currently a full microservices system because:

- All backend routers run in one FastAPI process.
- Services are organized as Python modules inside one backend.
- Database access is shared.
- ML inference runs in the same backend application environment.
- External integrations are called directly by the backend.

Internal layered organization:

Presentation layer:
   Frontend screens and components

API layer:
   FastAPI routers

Validation layer:
   Pydantic schemas

Business-logic layer:
   Backend services

Data-access layer:
   Motor/MongoDB operations

Infrastructure/integration layer:
   Cloudinary, Firebase, Gemini, news APIs

ML layer:
   YOLO, TensorFlow, and acoustic models


13. MAIN ARCHITECTURAL STRENGTHS
--------------------------------

- Clear separation between frontend and backend
- Modular FastAPI router structure
- Dedicated service layer for business logic
- Separate Pydantic schemas for validation
- Local model artifacts for specialized coconut analysis
- Supports both visual and acoustic analysis
- MongoDB provides flexible storage for user-generated content
- Cloudinary avoids storing large media files directly in MongoDB
- Firebase supports Google authentication and client-side persistence
- Expo allows one frontend codebase for mobile and web
- Market analysis, community, AI, and ML functionality are separated into
  distinct modules


14. IMPORTANT CURRENT LIMITATIONS
----------------------------------

1. The frontend navigation layout references several feature routes whose
   source files were not visible in the current frontend tree.

2. The backend currently uses permissive CORS configuration.

3. The backend is exposed through a development ngrok URL.

4. ML model loading is tightly coupled to the backend runtime.

5. Credentials and service-account files exist in the backend workspace and
   must be protected from commits and public distribution.

6. The frontend and backend configuration contain environment-specific URLs,
   so deployment requires updating configuration for each environment.

7. The system is a modular monolith; independent scaling of API, ML
   inference, and background processing is not yet implemented.
